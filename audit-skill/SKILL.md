# Audit Skill

## Purpose

Use this skill to produce evidence-backed audits that separate what was intended, what actually happened, what produced the result, and what can be honestly claimed.

The default stance is factual and non-shaming: identify mechanisms, provenance, drift, contamination, and correction language without moralizing.

## Core Rule

Never audit from filenames, summaries, labels, or claimed results alone. Audit from execution paths, source evidence, logs, timestamps, data lineage, and reproducible artifacts.

## Standard Workflow

### 1. Freeze The Audit Question

Restate the audit target before reading deeply:

- What was the original intent?
- What claim is being checked?
- What would count as valid evidence?
- What would count as contamination, drift, or a false positive?
- Which files, logs, outputs, and docs are in scope?
- Should the audit only report findings, or also create correction artifacts?

If the user has not specified whether edits are allowed, default to read-only and create new audit artifacts only.

### 2. Plan Before Reading Deeply For Complex Audits

For complex, ambiguous, or multi-branch audits, do a short structured planning pass first (on paper, or with whatever planning/reasoning tool you have). Use it to identify:

- root blockers
- dependency order
- competing interpretations
- parallel audit lanes
- hidden assumptions

Do not treat the trace as evidence. Treat it as a plan for gathering evidence.

### 3. Build An Audit Plan

Create a short checklist with statuses. Typical steps:

1. Establish stated intent and expected mechanism.
2. Inventory relevant files and artifacts.
3. Build a timestamp/provenance timeline.
4. Define evidence gates.
5. Inspect implementation paths.
6. Inspect logs/results and compare to implementation.
7. Classify each fork/component/result.
8. Write correction-ready conclusions.
9. Save audit artifacts, if requested.
10. Verify artifacts and report exact paths.

Update the checklist as work completes.

### 4. Inventory Artifacts

Use fast local search first:

- `rg --files`
- `rg -n "pattern"`
- list files sorted by modification time (`ls -lt`, or the equivalent on your OS)
- targeted reads of specific files and line ranges

Capture:

- scripts
- configs
- logs
- output files
- benchmark reports
- model/data artifacts
- docs and lab notes
- generated summaries
- timestamps

Do not infer chronology from numbering alone. Prefer file timestamps, log timestamps, commit history, and explicit dates.

### 5. Split Into Audit Lanes

For non-trivial audits, split the work by mechanism or risk class. Examples:

- source/runtime lane
- benchmark/results lane
- docs/narrative lane
- data lineage lane
- security/dependency lane
- reproducibility lane
- user-intent alignment lane

Use subagents when available and useful. Give each subagent raw artifacts and a narrow question. Avoid giving the desired conclusion.

### 6. Define Evidence Gates

Before judging results, define mechanical tests.

Example gate format:

```text
Valid if:
- code calls A, B, C
- logs show X
- output Y is produced from input Z

Invalid/contaminated if:
- code calls substitute path P
- benchmark uses oracle/target leakage
- runtime loads forbidden component Q
- result was generated by a different model/task than claimed
```

Use gates to prevent drift. If the evidence gate changes after inspection, state why.

### 7. Inspect Mechanism, Not Labels

For each artifact, answer:

- What code path actually runs?
- Which model/data/weights are loaded?
- Which functions produce the reported output?
- Are outputs generated, retrieved, filtered, hand-routed, cached, or benchmark-selected?
- Does the implementation match the stated experiment?
- Are there oracle labels, target leakage, shortcuts, hard-coded routes, or post-hoc selection?
- Are results from the same model, dataset, task, and metric being compared?

When code and docs disagree, code/logs win. When logs and code disagree, explain the uncertainty.

### 8. Classify Findings

Use clear labels. Suggested default taxonomy:

- `clean`: matches stated intent and evidence gates
- `valid-but-different`: technically valid, but answers a different question
- `partial`: some intended mechanism is present, but important caveats remain
- `contaminated`: result depends on hidden/unstated mechanism, leakage, wrong runtime, wrong data, or wrong comparison
- `invalid`: cannot support the stated claim
- `unknown`: insufficient evidence

Prefer neutral wording:

- "This branch used a hand-written routing rule, not the learned component it was named after."
- "This benchmark is an oracle upper bound, not deployment performance."
- "This is valid as a hybrid test, not as the fully automatic version that was claimed."

Avoid shame language:

- Do not write "fake" unless the user explicitly wants that wording.
- Prefer "mislabelled", "contaminated", "not evidence for that claim", or "different experiment".

### 9. Track Claim Corrections

For every incorrect or ambiguous claim, write:

```text
Do not say:
  <old claim>

Say:
  <corrected claim>

Because:
  <source-grounded reason>
```

This makes the audit directly usable for lab notes, papers, blog posts, READMEs, and memory updates.

### 10. Produce Audit Artifacts

Choose artifacts based on user need:

- concise findings memo
- CSV fork/component table
- post-mortem Markdown
- correction checklist
- source evidence appendix
- publication-safe claims section
- risk register

For CSV audits, useful columns are:

```text
id, component_or_fork, claimed_intent, actual_mechanism, key_evidence, verdict, corrected_claim, residual_risk
```

For post-mortems, useful sections are:

- Executive conclusion
- Original intent
- Valid vs invalid mechanisms
- Timeline
- Deviation point
- Recovery point
- Evidence
- Corrected public language
- Remaining uncertainty

### 11. Verify Artifacts

After writing any audit artifact:

- confirm file exists
- confirm size/line count
- sample key sections
- search for required phrases
- verify paths and timestamps
- report exact absolute paths

If existing logs/docs were edited by another agent, verify those edits by searching for the corrected claims.

## Generic Audit Checklist

Use this checklist directly when a user says "audit this":

```text
[ ] State original intent and audit question
[ ] State allowed actions: read-only, new artifacts, or edits
[ ] Do a structured planning pass if complex
[ ] Inventory files, logs, outputs, docs, timestamps
[ ] Build source-of-truth timeline
[ ] Define valid/invalid evidence gates
[ ] Inspect implementation paths
[ ] Inspect data lineage and benchmark setup
[ ] Inspect generated docs/results for claim drift
[ ] Classify each component/fork/result
[ ] Identify first deviation point
[ ] Identify recovery point, if any
[ ] Write corrected claims
[ ] Save audit artifact(s)
[ ] Verify artifact(s)
[ ] Report conclusions with file references
```

## Output Style

Lead with conclusions, then evidence. Keep tone direct and factual.

Use exact local file references when possible. Include line references for code evidence. Keep summaries separate from findings so the audit does not bury risk.

When asked for a public-facing correction, write in neutral language:

- "This result should be described as..."
- "This does not support the stronger claim that..."
- "The honest interpretation is..."

## Common Failure Modes To Catch

- filenames imply a mechanism that code does not use
- benchmark selected best result using target labels
- comparison mixes different tasks or models
- runtime silently loads forbidden components
- generated output comes from fallback path
- docs turn a side experiment into the main thesis
- post-hoc results are reported as pre-registered
- cached artifacts are mistaken for new computation
- a component that was supposed to be removed is quietly reintroduced under a new name
- "works" means demos succeeded, not benchmark passed
- eval parser bug changes the interpretation
- branch/fork inherits contamination from parent script

## Stop Conditions

Stop and ask the user only if:

- required evidence is missing and cannot be reconstructed
- the requested audit would require destructive actions
- the user asks to edit authoritative records but the correction is uncertain
- private/public disclosure boundaries are unclear

Otherwise, continue through artifact creation and verification.
